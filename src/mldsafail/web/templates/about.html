About this challenge

A reproducible benchmark for competing on tiny lattice problems inspired by ML-DSA.

A research environment that asks which computational primitive best proxies attacking small ML-DSA-like lattice instances — and lets manual researchers and coding agents compete on the same deterministic toy instances.

What is this?

This repository is an experimental benchmarking platform inspired by ECDSA.fail. It explores a single question:

Which isolated cryptanalytic subproblem is the most useful proxy for attacking small ML-DSA-like lattice instances — and how efficiently can implementations solve it on deterministic toy instances?

The long-term research interest is post-quantum cryptography, especially ML-DSA / Dilithium-like lattice structures. The transcript that motivated this project proposed lattice basis reduction (LLL/BKZ-style reduction, or whatever reduction procedure turns out to be most relevant) as a candidate primitive to isolate. The benchmark is intentionally primitive-agnostic at the top level: a solver profile is a concrete task, not a claim about the final target. The current codebase does not yet ship a basis-reduction profile; it ships a different concrete task below as a starting point for measurement.

The initial concrete task is a bounded short-vector recovery profile: a solver receives a public matrix A and a target t = A·s (mod q) and must recover the short vector s — one whose coefficients lie inside a small range [-η, η]. That profile is shipped so we can start measuring, not because the research question is settled.

Every executable experiment operates on deliberately small, locally generated instances — never on real cryptographic keys or deployed parameters. The tiny instances are the point: they are toy proxies chosen so meaningful optimization is measurable, the way a 40-bit toy key would be chosen as an experimental stepping stone rather than a real security target.

What the challenge asks on a given profile

Each profile defines a concrete task, a fixed modulus, fixed dimensions, and a fixed bound. For the current first profile, a solver receives a public matrix A and a target t = A·s (mod q). The solver attempts to recover the hidden short vector s while using as few abstract operations as possible. The matrix, the modulus, and the bound are fixed ahead of time by a repository-controlled profile; the solver never sees the planted solution, and an independent verifier checks every candidate from the public data alone.

Future profiles may change the task. The benchmark is supposed to stay flexible enough to isolate a different primitive if the research says so.

How a run works

Every experiment follows the same loop:

  1. Generate. A repository-controlled instance generator produces a deterministic problem from a recorded seed.
  2. Solve. A solver (written by a researcher or a coding agent) attempts the profile's task.
  3. Verify. An independent trusted verifier checks the candidate against the public data. Incorrect results are rejected.
  4. Score. Valid runs produce a versioned headline score. The current scoring mechanism is a weighted abstract operation count; it is an implementation decision, not a decision handed down by the source conversation. Runtime, memory, solution quality, and per-operation breakdowns are retained as diagnostics.
  5. Record. The experiment is appended to an immutable JSONL log with seeds, environment, source revision, hypothesis, and verification result.

The leaderboard

The headline score is the only ranking signal. The lowest valid full-suite score wins. Runtime, memory, solution quality, and per-operation breakdowns stay visible as diagnostics but never create competing winners. Records are grouped by deterministic scope — public and hidden seed suites with small, medium, and large profiles — so that comparisons stay fair and seed-specific overfitting is exposed.

Who is this for?

Researchers and agentic coding systems that want a reproducible, fair, and auditable environment for studying algorithmic improvements on lattice problems. Failures stay visible. Every experiment carries its hypothesis. The log is append-only and deterministic — the same inputs always produce the same record.

Safety boundary

This is a benchmark, not an attack tool. The project never accepts external public keys, signatures, or arbitrary cryptographic targets. Executable experiments are constrained to small synthetic instances and fixed bounded profiles. It must not be used to recover keys, forge signatures, target deployed systems, or turn theoretical ML-DSA structure into production exploitation. Work involving real ML-DSA should remain specification study, official correctness vectors, asymptotic analysis, or theoretical resource estimation.
