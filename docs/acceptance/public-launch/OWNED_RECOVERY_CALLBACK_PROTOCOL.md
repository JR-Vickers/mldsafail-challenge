# Dedicated native recovery callbacks

Execute these source-reviewed callbacks through the owned generic native driver, in the same Python process and under its continuous provision lease. The private driver configuration binds the clean source commit, callback SHA, helper family SHA, preloaded immutable image ID, exact image archive SHA, native operator domain, and separately owned daemon and whole-worker domains. No shared staging daemon is eligible.

`scripts/native_recovery_service_verification.py` (module `scripts.native_recovery_service_verification`, function `callback`) invokes the disposable migration-complete service fixture. Use an image providing `sh`, `sleep`, and `true`, with no declared anonymous volumes. It binds the actual native image inspection to the full configured immutable ID; archive-loaded images need no registry digest. The existing fixture records SIGTERM, SIGKILL, synthetic connection-loss owner termination, and deliberately failed cleanup followed by independently retryable cleanup. It checks exact service identities, original states, completed migration counter, concurrency rejection, signals, child quiescence, and final resource inventory. Both native behavior and cleanup must pass. The synthetic connection-loss case does not independently establish an actual SSH transport-drop gate.

`scripts/native_synthetic_database_restoration.py` (module `scripts.native_synthetic_database_restoration`, function `callback`) requires the approved immutable PostgreSQL image. It creates two distinct tiny network-isolated, resource-limited databases, dumps one to a sealed custom-format archive, restores into the other, and compares the exact schema and repository-generated public tiny fixture. All owned container/client cleanup is attempted before the acceptance receipt. Raw dump and authority journals remain private.

Both callbacks require final outer driver cleanup as well as their own cleanup. Preserve failed callback and outer-driver evidence; never promote a partial receipt. These gates establish disposable service restoration and synthetic logical restoration only. They do not establish approved off-host storage, independent owner password custody, private staging epoch restoration, production readiness, or benchmark performance. Actual changed-boot restoration has separate source-bound disposable VM evidence.
