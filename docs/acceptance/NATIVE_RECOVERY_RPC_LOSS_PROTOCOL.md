# Operational Journal create/start response-loss acceptance

This is a source-bound operational fault gate, separate from the accounting guardian fault suite. Invoke `scripts.native_recovery_rpc_loss.callback` through the generic owned native driver, using a new dedicated operational rootless daemon, distinct worker/operator domains and an exact approved preloaded fixture image with `/bin/sh`, `sleep` and no declared anonymous volumes. Both source/review and image/archive identities must be retained in the private driver configuration. Never use the default staging Docker daemon. No epoch or CPU benchmark measurements run.

The predeclared sequence contains exactly two probes: create response loss, then start response loss. Each uses a new Journal and a network-isolated 32-MiB/16-PID tiny sleep container. The gated Docker CLI is directed to a private diagnostic Unix socket by its explicit `--host` argument; operational scope registration still verifies the real dedicated daemon. The proxy relays bounded native health preludes and the declared POST only. It retains the actual successful daemon response (201 create or 204 start), then closes transport without delivering that acknowledgement. A generic CLI failure or timeout alone cannot establish this gate.

The complete diagnostic executor and all its sockets must be quiescent before any Journal repair/restart. Then actual `Journal.cleanup` must establish its strict old-epoch whole daemon/worker barrier, stop creator domains, durably register a fresh epoch, remove known fixture containers and pass inventory cleanup. The callback independently reads the exact versioned proof, validates current environment, and repeats cleanup without another mutation or changed epoch. Both probes and the outer driver terminal barrier must pass. A failed probe stops further probes and retains partial receipts. Publication errors retract positive dispositions through an independent negative retry.

This gate proves lost acknowledgements for the operational recovery Journal; owner signals, kernel power loss, actual SSH transport loss, local protected epoch restoration and off-host recovery remain separate gates. The callback does not claim shared-staging RPC repair authority, production activation or any score/threshold change.
